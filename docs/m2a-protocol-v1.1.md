# M2a Experimental Protocol v1.1

**Status:** Phase 0 draft for review. Do not begin Phase 1 code until this protocol, the catalog schema, the proposed mechanism matrix, and all independent oracle specifications have been reviewed. M1.1 acceptance remains a separate gate. Fault mechanisms and numerical thresholds must be justified before the development split is implemented; all evaluation choices are frozen at the Phase 3 checkpoint.

## Objective and limits

M2a tests whether diagnosis, including controlled counterfactual replay, improves localization of silent data corruption over simpler methods on the documented NYC TLC Yellow Taxi pipeline. It is not a formal verification result and does not support claims about arbitrary enterprise pipelines. The contract declares expected behavior; runtime checks observe it; independent references establish correctness where available; diagnosis ranks causes; interventions test explanations; and the publication gate decides whether outputs can be released.

The M1 January 2024 evidence remains bound to its historical contract hash and is not rewritten to match a later contract. M2a uses a separately versioned contract v2 where TLC columns vary across the selected years. A valid historical evidence bundle remains valid if the repository contract later changes; its verifier reports the current-contract comparison separately.

## Fault catalog and independent evidence

Phase 0 produces and reviews three versioned artifacts before Phase 1 code: `schemas/fault-catalog-v1.schema.json`, `experiments/m2a/catalog/fault_catalog_v1.json`, and `docs/m2a-independent-oracles-v1.md`. The draft catalog contains eight distinct mechanisms, two per stage. Each split has one whole mechanism from every stage, and each split includes both contract-visible and contract-silent externally detectable cases. Each mechanism has three declared severities and seeds 11, 29, and 47, yielding 72 repeated executions. These variants are not 72 independent mechanisms. The catalog author knows the held-out assignments; this is disclosed as a limitation. The mechanism list is a reviewed proposal, not a quota: remove a mechanism if its oracle or meaningful severity cannot be established, and document any resulting split limitation.

Before M2a code, create a versioned catalog with one record per mechanism: stable ID, stage, transformation, locus (`code_fault` or `data_fault`), class, exact deterministic mutation and parameters, severity, seed, original-implementation behavior, affected records/keys/partitions/metrics, oracle, available evidence, expected detectability, impact function and tolerance, and split. Fault classes are:

- `contract_visible`: violates an existing declared invariant.
- `contract_silent_externally_detectable`: passes declared checks but conflicts with an independently justified oracle or additional production-available evidence.
- `underdetermined`: available evidence cannot distinguish the correct and faulty results. This is an observability limit, not an ordinary recall miss.

Every detectability label has a written rationale and is frozen before detector tuning. Cases are not reclassified after results. The injector owns private execution labels and mutation parameters; the detector receives a separate allow-listed input bundle with no mutation details, expected outputs, evaluator labels, or oracle-derived hints. Test the assembled detector bundle for leaked fields as well as failing on any attempt to open a path whose basename begins `ground_truth`. The evaluator uses separate private labels and calculations.

Catalog mechanisms are selected before fixing the matrix. Each selected case must have a meaningful independent oracle and severity. Reference transformations are checked against hand-computed fixtures and separate reconciliation; they are not trusted merely because they differ from the faulty code. When an oracle establishes only part of the output, score only those properties. The catalog author knows the holdout assignment, which remains a threats-to-validity limitation; no broad mechanism-generalization claim is made from a handful of held-out mechanisms.

Hooks are owned by the harness and placed at ingestion, cleaning, join, and aggregation boundaries. They are invisible to the detector and absent from reference code paths. The initial target is two distinct mechanisms per stage, with three meaningful severities and three deterministic seeds where applicable. Hold out whole mechanisms while keeping both detectable classes and all included stages represented. If independence and representation conflict, document the limitation instead of splitting close variants and calling them independent.

## Detection and diagnosis protocol

Detection and diagnosis have separate result tables. The detection table compares the full system under test, consisting of contract rules plus frozen silent-fault checks, against row-count-only, schema-only, and contract-rule-only detectors. All receive the same legitimate production inputs and evidence. The silent-fault checks must be justified by source documentation, domain invariants, or general pipeline conservation, not selected by inspecting held-out outcomes. Disclose each added check and freeze its thresholds before held-out generation. Timestamp-distribution checks use clean controls and may alert or block only under the predeclared schema-cohort and baseline-window criteria.

Keep two result tables. The detection table has four arms: the full system under test, row-count-only, schema-only, and contract-rule-only. The diagnoser table has four arms: lineage-only, observed-divergence from ordinary pipeline logs, reference-assisted divergence using trusted stage outputs, and counterfactual replay. For the conditional diagnosis comparison, the frozen full-system detector's production-visible alert is the common trigger: every diagnoser receives the same alerted cases and only the evidence allowed for its method. Report diagnosis accuracy on that common alerted subset. Separately report end-to-end success over all eligible cases, which requires a correct alert, correct localization, and a successful oracle-validated intervention. Never describe counterfactual replay as a detector.

Counterfactual replay supports two intervention types:

1. `replace_transformation`: replace one identified code transformation with a validated reference transformation.
2. `replace_input`: replace one corrupted data input with a trusted version, then replay the downstream stages from the same upstream inputs.

Each catalog case declares its locus and eligible intervention type. Input replacement is available only when an independent trusted input exists. A data fault is not considered repaired merely by rerunning correct code on the same corrupted input. Interventions replay affected downstream stages, compare every oracle-supported result, and report residual damage. At most four ranked single-stage interventions are run per alerted case; stop on a complete oracle match or after attempt four. Report attempt count, replay time, peak memory, diagnosis before and after, and unresolved or partial repair. Do not combine multiple faults in M2a.

## Controls, metrics, and analysis

Use January 2022 through December 2025: 2022 supplies the 12-month warm-up, and January 2023 through December 2025 are the 36 scored monthly runs. This recent period uses zone IDs and avoids older coordinate-based TLC schemas. Before contract v2 is written, inspect and record the schema, types, and data-dictionary applicability for all 48 source months. Keep the M1 evidence tied to its historical contract hash. A month is `independently_verified_clean` only when its immutable official source checksum is recorded, Polars `1.44.2` recomputation independently agrees on declared per-stage row counts, null counts, exact fare sums, and join multiplicities, and its columns, types, date coverage, and applicable ranges satisfy the TLC data dictionary. Implement this recomputation in Polars as a separate calculation from the DuckDB pipeline. Findings are classified separately as independently verified clean, genuine source anomaly, or unresolved/disputed source anomaly. A genuine source anomaly correctly detected by the pipeline is not a false alarm.

The statistical baseline window is exactly the preceding 12 eligible months from the same contract, source-schema cohort, and declared operating regime, with calendar-month, weekday, and hour strata where applicable. The January 2025 congestion-pricing change starts a separately reported regime stratum. Do not compare its distribution to the pre-change regime. A month without 12 eligible same-regime history months is ineligible for a distribution alert; report that status and keep exact reconciliation checks active. Mark the 2022 warm-up months as calibration-only, not scored controls. Known regime breaks and independently identified source anomalies are excluded from statistical calibration and reported. Thresholds and alert/block conditions are fixed on development controls before held-out evaluation.

The false-positive unit is one independently verified clean monthly run with the relevant check eligible. Report separate numerators and denominators for the full run-level decision and distribution-check-only alerts, with binomial intervals where assumptions are defensible and dependence caveats for shared source generation and pipeline configuration. Report the 36-month target separately from any reduced observed denominator. Report source-anomaly detections and unresolved findings separately. Fault recall uses the mechanism as the inference unit: give detected and missed mechanism counts and descriptive per-mechanism results. Severity and seed executions are correlated repeats, not independent mechanisms. Do not pool them to imply a large sample; any interval must state and justify its independent unit. With four held-out mechanisms, results are descriptive and no pooled generalization claim is made.

For every run, record whether it was published, blocked, or abstained; whether that decision was correct against the independent oracle; and whether a fault escaped publication. Report alerting, localization, root-cause rank, impact accuracy, and causal validation as separate outcomes. Top-1 is primary. Do not report top-3 with four stage candidates. Impact metrics are mechanism-specific: exact row/key differences, absolute and relative numeric error, or declared distribution comparisons. For zero, null, or values below a predeclared epsilon, report absolute error and omit unstable relative error. ML impact is deferred.

Report alert time, validation overhead, diagnosis time, and publication-decision time separately. Compare detector-enabled and detector-disabled runs in fresh subprocesses on the same data and environment, at least five repetitions, reporting distributions. Peak working set is a controlled empirical comparison, not exact attribution of allocated bytes.

## Freeze, held-out generation, and reproducibility

The development and held-out mechanisms, split assignment, catalog, deterministic generation procedure, oracle definitions, detector code, thresholds, candidate ranking, scoring rules, analysis plan, and all relevant configuration hashes are frozen before held-out evaluation. Record hashes for the catalog, split, generator, references, detector, configuration, scoring, and analysis plan; record the held-out case-list hash. Tag that complete frozen state `m2a-frozen` before generating or revealing held-out labels. Held-out labels, mutation parameters, and any private generation seed or manifest remain evaluator-only and inaccessible to detectors and tuning.

Generate cases from the precommitted catalog and deterministic procedure after the freeze. Persist one immutable result record per case containing catalog ID, split, seed, severity, input hashes, run outcome, checks, localization, impact, intervention attempts, runtime, memory status, and output hashes. Write each case atomically with a completion marker. On Kaggle resume, load a prior versioned result bundle, verify its hashes and frozen code/configuration identities, skip only complete matching cases, and rerun incomplete or mismatched cases. Preserve raw per-case outputs for the evaluator; generate all tables from those raw records with one command.

The current M1 sample uses about 50 to 59 MB per monthly Parquet input and about 77 MB of materialized clean-run outputs. Planning estimate for 36 scored months is 1.8 to 2.2 GB of raw inputs and about 2.8 GB of clean outputs; include warm-up inputs when estimating source storage. Retaining a baseline plus four replay materializations for 72 scenarios could approach 28 GB before controls and scratch; reserve 40 GB if retaining all Parquet outputs. Persist compact, atomic results and hashes per case, retain all clean-control outputs and only necessary replay Parquet, and verify the prior bundle's hashes and frozen-code/configuration identities before resuming Kaggle work. A three-month pilot is required before the full workload. The planning estimate is roughly 8 to 10 seconds per pipeline run, so a few hundred executions may fit one Kaggle session; measure pilot runtimes and storage before relying on that estimate.

If a defect is found in the frozen detector or protocol, create a new version and a new untouched holdout. Do not patch and rerun the same cases while calling them untouched. The December 15, 2026 checkpoint is a scope decision, not a deadline for scientific claims. At the November 24 checkpoint, reduce scope if needed. The reduced engineering benchmark may use three stages and two mechanisms per stage, with whole held-out mechanisms; it is not equivalent evidence for the four-stage design. If that reduced split cannot credibly represent both detectable classes, publish the limitation and observed results without a generalization claim.

## Acceptance and threats to validity

M2a is accepted only when `m2a-frozen` exists; one command reproduces evaluation from the persisted raw per-case outputs; scripts generate every result table; an independent results verifier passes and detects altered or missing evidence; and the report includes misses, false alarms, ambiguous diagnoses, residual damage, resource distributions, and a threats-to-validity section. Report the number of distinct mechanisms detected and missed. Do not treat 72 severity/seed scenarios as 72 independent mechanisms.

The threats-to-validity section must cover catalog-author knowledge of the split, small held-out mechanism count, source-month dependence, TLC source anomalies, schema-version and regime boundaries, oracle incompleteness, threshold selection, detector evidence access, and the limited scope of the dataset. A defect in the frozen implementation invalidates that version's held-out result; it requires a new version and new holdout.

The scope checkpoint is December 15, not a deadline for scientific claims. State clearly that a reduced benchmark is not equivalent evidence for the four-stage design.
